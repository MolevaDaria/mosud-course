# Практическая работа № 8. ER-модель и расширение предметной области

**Вариант 6.** Расширение: Попытки доставки (`shipments`, `delivery_attempts`, `delivery_events`).

## 1. Описание ER-модели

На диаграмме (`erDiagram.png`) представлены три новые сущности, связанные с таблицей `olist.orders`:

* **shipments** (отправки) — хранит информацию о конкретной отправке заказа (перевозчик, трекинг-номер, дата отправки).
* **delivery_attempts** (попытки доставки) — фиксирует каждую попытку вручную доставить заказ (успех, неудача, перенос).
* **delivery_events** (события доставки) — лог всех событий, произошедших с отправкой (забран со склада, в пути, доставлен).

**Кратности связей:**
* `olist.orders` → `shipments`: **1:N** (один заказ может быть разбит на несколько отправок).
* `shipments` → `delivery_attempts`: **1:N** (по одной отправке может быть несколько попыток).
* `shipments` → `delivery_events`: **1:N** (у одной отправки может быть цепочка событий).

## 2. Бизнес-правила и ограничения

| № | Бизнес-правило | Реализация в DDL |
|---|---|---|
| 1 | Отправка всегда относится к существующему заказу | `fk_shipments_order` (FK → `olist.orders`) |
| 2 | Статус отправки может быть только из фиксированного списка | `ck_shipments_status CHECK (status IN ('created','in_transit','delivered','failed'))` |
| 3 | Трекинг-номер уникален для каждой отправки | `uq_shipments_tracking UNIQUE (tracking_number)` |
| 4 | Номер попытки доставки должен быть положительным | `ck_delivery_attempts_attempt_number CHECK (attempt_number > 0)` |
| 5 | Результат попытки — только `success`, `failed` или `rescheduled` | `ck_delivery_attempts_result CHECK (...)` |
| 6 | В рамках одной отправки не может быть двух попыток с одинаковым номером | `uq_delivery_attempts_shipment_number UNIQUE (shipment_id, attempt_number)` |
| 7 | Тип события доставки — из фиксированного списка | `ck_delivery_events_type CHECK (...)` |
| 8 | Все ключевые поля (ID заказа, перевозчик, дата отправки) обязательны | `NOT NULL` на `order_id`, `carrier_name`, `shipped_at` |
| 9 | При удалении отправки удаляются все её попытки и события | `ON DELETE CASCADE` на FK |
| 10 | Первичные ключи — суррогатные (`SERIAL`) | `pk_shipments`, `pk_delivery_attempts`, `pk_delivery_events` |

## 4. Ответы на контрольные вопросы

1. **Когда связь M:N требует отдельной таблицы?**
   Когда один объект может быть связан с несколькими объектами другого типа, и наоборот. В нашем случае связи строго 1:N (одна отправка -> много попыток), поэтому отдельная таблица для связи не нужна. Если бы, например, одну отправку можно было разделить на несколько посылок разных перевозчиков, потребовалась бы таблица-связка.
   
2. **Чем естественный ключ отличается от surrogate key?**
   Естественный ключ (natural key) — это атрибут предметной области (например, `tracking_number`). Суррогатный ключ (surrogate key) — искусственно созданный идентификатор (например, `SERIAL shipment_id`). Суррогатные ключи удобнее для внешних ключей, так как они не меняются со временем и имеют фиксированный размер.
   
3. **Какие ограничения лучше реализовывать декларативно, а не триггером?**
   Декларативно реализуются ограничения, проверяющие данные в пределах одной строки (`CHECK`, `NOT NULL`), уникальность значений (`UNIQUE`, `PRIMARY KEY`) и ссылочную целостность (`FOREIGN KEY`). Триггеры нужны для сложных межстрочных проверок (например, «сумма всех попыток не должна превышать лимит» или «дата события не может быть раньше даты отправки»), которые нельзя выразить простым `CHECK`.
