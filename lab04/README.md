# Практическая работа № 4. Соединения отношений и сложные JOIN

**Вариант 6.** Сценарий: Повторные покупатели. 
Маршрут: `customers` по `customer_unique_id` → `orders` → `order_items`.

## 1. Основной запрос (Пункт 1)
Основной запрос использует **три таблицы**: `customers`, `orders` и `order_items`. Для каждого уникального клиента (`customer_unique_id`) вычисляется:
- количество уникальных заказов (`total_orders`),
- общее количество купленных товаров (`total_items`),
- дата первой и последней покупки.

Для избежания размножения строк при соединении с `order_items` количество заказов считается через `count(DISTINCT o.order_id)`.

## 2. Кратность связей (Пункт 2)
* `customers` → `orders`: **1:N** (у одного реального человека `customer_unique_id` может быть несколько записей `customer_id`, каждая из которых порождает заказ).
* `orders` → `order_items`: **1:N** (в одном заказе много товаров).
* Итоговая связь `customers` → `order_items`: **1:N** (через цепочку `orders`).

## 3. LEFT JOIN (Пункт 3)
Добавлен `LEFT JOIN` в запросе для вывода клиентов с 1 заказом (все клиенты в базе Olist имеют заказы, поэтому `total_orders` не равен 0, но запрос демонстрирует, как сохранить объекты без связанных строк).

## 4. Антисоединение (Пункт 4)
Запрос находит клиентов, у которых нет ни одного заказа. В Olist таких клиентов **0**, так как каждый `customer_id` появляется только при оформлении заказа. Запрос вернул 0 строк — это ожидаемый результат, демонстрирующий корректность антисоединения.

## 5. Ошибочный JOIN (Пункт 5)
Прямое соединение `customers` → `orders` → `order_items` без `DISTINCT` или предварительной агрегации завышает `count`. Например, для клиента `c8460e...` ошибочный запрос вернул `total_items_in_orders = 24`, хотя у него всего `4` заказа. Причина: строка заказа размножилась на количество позиций в нем.

## 6. Исправление ошибки (Пункт 6)
Через CTE `order_sums` мы сначала агрегируем `order_items` до уровня одного заказа (`count(*) AS items_in_order`), а затем соединяем с `customers` и `orders`. Теперь `total_orders` — реальное количество заказов (например, 4 для `c8460e...`), а `total_items` — сумма всех позиций (24). Размножения строк нет.

## 7. Реляционная алгебра (Пункт 7)
1. Переименование: ρ(c)(customers), ρ(o)(orders), ρ(oi)(order_items).
2. Соединение (⋈): `customers ⋈_{customer_id} orders ⋈_{order_id} order_items`.
3. Проекция (π): выборка `customer_unique_id`, `order_id`, `order_item_id`, `order_purchase_timestamp`.
4. Агрегация (γ): группировка по `customer_unique_id`, вычисление `count(DISTINCT order_id)`, `count(order_item_id)`, `min`/`max` timestamp.
5. Выборка (σ): фильтрация `total_orders > 1`.

## 8. Контрольные вопросы
1. **Почему соединение order_items и order_payments по одному order_id может завысить SUM?**
   Если в заказе 3 товара и 2 платежа, прямое соединение даст 3 × 2 = 6 строк. Сумма будет посчитана 6 раз (каждый товар умножится на каждый платеж), что завысит итоговую сумму.
2. **В чём отличие LEFT JOIN ... WHERE right.id IS NULL от NOT EXISTS?**
   `LEFT JOIN ... IS NULL` сначала выполняет соединение (что может быть ресурсоемко при больших таблицах), а потом фильтрует. `NOT EXISTS` использует полу-соединение и останавливается, как только находит первое совпадение, что часто работает быстрее и лучше оптимизируется планировщиком.
3. **Как представить эквисоединение через декартово произведение и выборку?**
   Эквисоединение `R ⋈_{R.a = S.b} S` математически эквивалентно `σ_{R.a = S.b}(R × S)`. Сначала берется декартово произведение (все пары строк), а затем выборка (WHERE) оставляет только те пары, где условие равенства выполняется.
